* [order management domain](https://github.com/TuralSuleymani/production-ready-DDD-EDA-Azure/tree/main/src/VOEConsulting.Flame.OrderManagement.Domain)
  * This is our aggregate route domain driven design.
  * 2 main parts, strategic and tactical patterns.
  * tactical pattern perspective - having aggregates, entities, value objects, modules, repositories, factories and more.
  * from the development perspective for your domain layer, you are actively adding entities, value objects, aggregates, domain events, services to this layer.
  * [order code](https://github.com/TuralSuleymani/production-ready-DDD-EDA-Azure/blob/main/src/VOEConsulting.Flame.OrderManagement.Domain/Orders/Order.cs)
      * order is a classical class, not a DTO. Because it has some sort of business behavior.
      * It is a rich domain model rather than a class that has get/set.
      * cancel method is business element, markshipped method is also a business behavior, rather than a class with multiple get/set properties.
      * And this DDD approach with aggregate route helps us to raise domain events in our aggregate route design.
      * AggregateRoot<Order> -  have prepared a separate project [Flame domain common](https://github.com/TuralSuleymani/production-ready-DDD-EDA-Azure/tree/main/src/VOEConsulting.Flame.Domain.Common)
        * all the base classes related to aggregate routes, value objects, entities, et cetera.
        * Our aggregate route allows you to have events. Because in our business side, we need to understand what's happening.
        * Send this events to other services because other services also need some (mandatory) information regarding to the business processes that happen in our microservice.
        * cancel/MarkShipped method - raising a domain event  RaiseDomainEvent(new OrderCancelledEvent(Id.Value, DateTimeOffset.UtcNow, OrderId));
  * the domain layer is all about having business components.
  * the real domain elements, order ->  MoneyBreakdown pricing -> have a lot of interesting value objects here.  
      * [MoneyBreakdown.cs](https://github.com/TuralSuleymani/production-ready-DDD-EDA-Azure/blob/main/src/VOEConsulting.Flame.Domain.Common/ValueObjects/MoneyBreakdown.cs)
      * this is our value object because in domain-driven design, we are actively creating value objects to encapsulate our business inside value objects.
  * Mostly with DDD -> actively using value objects rather than aggregates and entities.
  * Most of the elements, the business processes considered inside our value objects.

    * for example, placing order, using [CQRS command handlers](https://github.com/TuralSuleymani/production-ready-DDD-EDA-Azure/blob/main/src/VOEConsulting.Flame.OrderManagement.Application/Orders/Commands/PlaceOrder/PlaceOrderCommandHandler.cs)
    * command handler is actively using aggregate with repository.
    * In order to construct this aggregate, we actually need some sort of entities, value objects.
    * applying this value objects here. But the main part our user places a new order.
    * <img width="450" height="450" alt="image" src="https://github.com/user-attachments/assets/278155e0-c0d9-4ef5-a648-01dbb58aefaa" />
    * Action will return this process because I have implemented a template method pattern here. -  OrderCommandHandlerBase<PlaceOrderCommand> -> ExecuteAsync()
    * ExecuteAsync() -> abstract method because have a small framework which have implemented using template method pattern and response from this implementation, calling order repository and saving all this stuff together.
    * Because this order repository is actually an implementation form of Cosmos DB [Cosmos order repository](https://github.com/TuralSuleymani/production-ready-DDD-EDA-Azure/blob/main/src/VOEConsulting.Flame.OrderManagement.Infrastructure/Cosmos/CosmosOrderRepository.cs#L44) -> using transactional batch here.
        * Because when you send a request -> doing more than one operation.
        * For example, in a transactional context, may an update to tables at the same time, which you are creating a transaction.
        * When the parts of your system is actually a different technologies, like using entity framework to store my data. But want to send information to Apache Kafka.
        * how you can make these two operations a transactional operation. That's why we created Cosmos order repository, which uses a transactional batch.
